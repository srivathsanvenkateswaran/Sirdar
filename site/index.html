A ticket arrives. Something reads it first.

Sirdar gathers the evidence a support ticket needs, in the customer's own language, and writes a root-cause note for you to review. A desktop app for macOS and Windows, and a command-line tool, over the coding agent you already pay for.

Download
go install github.com/srivathsanvenkateswaran/sirdar/cmd/sirdar@latest

Apache-2.0. It runs on your machine, on your logins, and it never writes to the tracker. The note is a hypothesis, not a verdict.

Five commands. You read the note between the third and the fourth.

  1. sirdar init

    Scaffolds .sirdar/config.yaml, the playbooks, and the git excludes.

    Nothing runs yet.

  2. sirdar doctor

    Checks that the provider CLI is installed and signed in, that each configured source answers, and that the notes directory and templates are usable.

    Still nothing runs.

  3. sirdar triage KEY

    Fetches the ticket host-side, runs one agent session in your workspace, writes a Triage Note.

    Reads only.

you read the note here

  1. sirdar fix KEY

    Implements that note's Proposed Fix on a branch in a linked worktree, commits, pushes, opens the pull request.

    Running it is the approval.

  2. sirdar rca KEY --pr URL

    Writes the RCA and the Resolution draft, and reviews whether the triage hypothesis held.

    Marks the note resolved.

The desktop app and sirdar serve start the same runs from a New session form, show them on a board, and stream each one as it happens. Same binary, same workspace, same notes.

Every run on one board. The rail is the legend.

Six lanes: queue, gathering, blocked, triaged, done, failed. One hue per state, on the lane rail and on every badge in that lane, so a run's state is never colour alone. The tracker's queue sits in the first lane and the day's webhook deliveries under them.

Three ways to read a run.

The Session window has three layouts. Pick one in Settings or from the switcher in the session header; the window remembers it.

  • Conversation

    The transcript as a chat, the answer as a card at its end, an inspector on the right.

  • Document

    The note or the change as the window, the path the agent took beside it.

  • Workbench

    Documents in tabs over a console of every call, with gauges in the header.

It drives the coding agent you already have.

Each one signs in with its own login. Sirdar spawns the CLI you are already signed in to and never stores or proxies a credential: no Sirdar account, no server, no telemetry.

The acp provider speaks the Agent Client Protocol, so one adapter covers the three above. The openai provider is Sirdar's own agent loop against any Chat Completions endpoint, a vendor's or a server on this machine. Cursor approves its own tool calls, so Sirdar cannot judge them first: a write that completes there fails the run, and fix refuses it. The marks are the vendors' trademarks, shown only to say which CLI a run is on.

Names set in Sirdar's own type, never a vendor's mark: a logo would imply an endorsement, and this is only a statement about what the adapters read. Anything not on the list is a separate executable speaking line-delimited JSON over stdin, named in config, so a vendor integration and its credentials never touch Sirdar's core.

It cannot write to your tracker.

Each line below names the mechanism, because a guarantee without a mechanism is a promise. Every run also carries a turn budget, a wall-clock budget and a USD budget, and one that goes silent for six minutes is cancelled rather than held to the end of the clock.

Never writes to the tracker or the helpdesk.
In any mode. No adapter has a write path. Sirdar reads tickets and writes notes to disk, full stop.
A triage session cannot edit files.
Each provider rests that on its own mechanism. Claude Code and Qwen Code run with their write tools off and every other call sent to Sirdar's policy to answer. Codex runs in its read-only sandbox with approvals on. The OpenAI-compatible loop is Sirdar's own, so it decides before each call. An ACP agent is put in its read-only session mode. Every segment of a compound shell command has to match a pattern from permissions.bash; substitution and redirection are refused.
Fetching is judged by destination, not by tool name.
permissions.fetch lists the hosts a session may reach and it is empty by default, so a workspace that has not said where a run may fetch from fetches nowhere. An instruction hidden in a ticket comment cannot pick the destination.
Fix is gated on a person.
It refuses to start unless the note's frontmatter status is triaged or fix-approved. There is no separate approval record: running the command is the approval. If the agent's fix deviated from the note, the commit is made and nothing is pushed.
The snapshot check, after every fix session.
sha256 of everything under .sirdar/ and under the directory git runs this repository's hooks from, before the session and again the moment it ends. Any difference fails the run before the first git command, so nothing is committed and nothing is pushed.
Your logins, your machine.
Credentials are written as env:NAME, keychain:SERVICE, file:PATH or cmd:COMMAND, never as a literal; a secret written out fails the first time the workspace loads. Sirdar spawns the provider binary you are already signed in to. No Sirdar account, no server, no telemetry.

Download.

Both come from the same GitHub release. Every release opens as a draft and a person publishes it.

The desktop app

macOS and Windows. sirdar-desktop_<tag>_<os>_<arch>.zip: unzip it and run the app inside.

On Windows the app needs Microsoft's WebView2 runtime. Windows 11 and current Windows 10 ship it; a machine without it opens a window and draws nothing, and the Evergreen Bootstrapper puts it right.

The builds are unsigned. macOS asks you to right-click the app and choose Open the first time; SmartScreen asks for More info, then Run anyway.

The CLI

macOS, Linux and Windows, amd64 and arm64. sirdar_<version>_<os>_<arch>.tar.gz (.zip on Windows), with checksums.txt beside them and deb and rpm packages for Linux. Put sirdar on your PATH.

Or from source, any commit, released or not:

go install github.com/srivathsanvenkateswaran/sirdar/cmd/sirdar@latest

About

On a Himalayan expedition the sirdar is the lead Sherpa: the one who assigns the team's work and answers for the outcome. The name is a tribute to the Sherpa people, whose work on the mountain makes every ascent possible and is rarely the part that gets photographed.
