A ticket arrives. Something reads it first.

Sirdar gathers the evidence a support ticket needs, in the customer's own language, and writes a root-cause note for you to review. The note is a hypothesis, not a verdict.

Install
brew install srivathsanvenkateswaran/sirdar/sirdar

The tap goes live with the first published release; until then go install github.com/srivathsanvenkateswaran/sirdar/cmd/sirdar@latest builds any commit.

Apache-2.0. It runs on your machine, on your logins, on a coding agent you already pay for: Claude Code, Codex, Qwen Code, or any OpenAI-compatible endpoint.

Anything not on the list is a separate executable speaking line-delimited JSON over stdin, named in config, so a vendor integration and its credentials never touch Sirdar's core.

Four commands. You read the note between the second and the third.

  1. sirdar init

    Scaffolds .sirdar/config.yaml, the playbooks, and the git excludes.

    Nothing runs yet.

  2. sirdar triage KEY

    Fetches the ticket host-side, runs one agent session in your workspace, writes a Triage Note.

    Reads only.

you read the note here

  1. sirdar fix KEY

    Implements that note's Proposed Fix on a branch in a linked worktree, commits, pushes, opens the pull request.

    Running it is the approval.

  2. sirdar rca KEY --pr URL

    Writes the RCA and the Resolution draft, and reviews whether the triage hypothesis held.

    Marks the note resolved.

It cannot write to your tracker.

Each line below names the mechanism, because a guarantee without a mechanism is a promise.

Never writes to the tracker or the helpdesk.
In any mode. No adapter has a write path. Sirdar reads tickets and writes notes to disk, full stop.
A triage session cannot edit files.
Edit, Write, MultiEdit and NotebookEdit are denied outright. Every segment of a compound Bash command has to match a pattern from permissions.bash; command substitution and redirection are refused, and so is an argument pointing outside the workspace root.
Fetching is judged by destination, not by tool name.
permissions.fetch lists the hosts a session may reach and it is empty by default, so a workspace that has not said where a run may fetch from fetches nowhere. An instruction hidden in a ticket comment cannot pick the destination.
Fix is gated on a person.
It refuses to start unless the note's frontmatter status is triaged or fix-approved. There is no separate approval record: running the command is the approval. If the agent's fix deviated from the note, the commit is made and nothing is pushed.
The snapshot check, after every fix session.
sha256 of everything under .sirdar/ and under the directory git runs this repository's hooks from, before the session and again the moment it ends. Any difference fails the run before the first git command, so nothing is committed and nothing is pushed.
Config carries references, not secrets.
Credentials are written as env:NAME, keychain:SERVICE, file:PATH or cmd:COMMAND. A webhook secret written out literally fails the first time the workspace loads, rather than the first time a hook fires.
Every run is bounded, and a silent one is cancelled.
A turn budget, a wall-clock budget and a USD budget. A session with no tool call, no text and no usage line for six minutes is marked failed rather than held to the end of the clock.
Your logins, your machine.
Sirdar spawns the claude, codex or qwen binary you are already signed in to, and never stores or proxies a credential. No Sirdar account, no server, no telemetry.

Six lanes. The rail is the legend.

The desktop app and sirdar serve show the same board. One hue per state, on the lane rail and on every badge in that lane, so a run's state is never colour alone.

About

On a Himalayan expedition the sirdar is the lead Sherpa: the one who assigns the team's work and answers for the outcome. The name is a tribute to the Sherpa people, whose work on the mountain makes every ascent possible and is rarely the part that gets photographed.
