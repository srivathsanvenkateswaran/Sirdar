Recording a customer return adds its quantity to stock twice, so on-hand stock drifts above the movement report

Triage note · written by the agent at 03:13 after your steer·notes/SBX-1 recording-a-customer-return-adds-its-quantity-to-stock-twice.md·Ticket: Product 00219 stock shows 1 more than the movement report
Root causecode · confidence high

In Ledger.ApplyMovement, the Return case adds the return quantity to the running stock twice: once directly at ledger.go:33E1 and again through l.restock at ledger.go:34E1, which does its own += at ledger.go:45E1. The movement report (SumMovements/Movement.Delta) counts a return once, as +Quantity E2 E3. After any return, on-hand stock therefore sits above the report by that return's quantity. A 1-unit return gives the +1 gap the customer sees E9. The code comment at ledger.go:28-32 describes this double application: restock used to be the only increment, driven by a separate "item scanned back in" event, and a direct increment was added without removing it. Purchase, Sale and Adjustment each apply their quantity once, with the same sign Delta uses, so Return is the only case that disagrees E4. I have not confirmed this against the customer's actual data because no log, APM or database source is configured for this run.

Partial returns are affected too. This module has no separate partial-return path, so returning fewer units than were sold is an ordinary Return movement with a smaller Quantity and is double-counted by that amount E6.

Proposed fixledger.go · ledger_test.go

Apply a return's quantity once in ApplyMovement. The smallest change is to delete one of the two increments in the Return case: either remove line 33 and keep restock, or remove the restock call at line 34 along with the now-unused restock helper at ledger.go:43-46, since rg shows no other caller. A sturdier option is to fold every movement type with l.Stock[m.ProductID] += m.Delta(), so the running total and the report share one sign rule and can't diverge again. Add a regression test in ledger_test.go: Purchase 10, Return 1, then assert CurrentStock == 11 and Reconcile ok. After deploying, any stock already inflated by past returns needs to be recomputed from the movement history.

Remediation SQL: none provided. No database source is configured for this run and this module keeps Stock as an in-memory running map (ledger.go:5-8), so I don't know the persistence layer or table names and won't guess at SQL.

Risks: if the separate "item scanned back in" event mentioned at ledger.go:28-31 still exists in some other service or integration and adds stock on its own, returns may be counted more than twice in production, and removing only one increment here wouldn't fully close the gap. A stock rebuild changes the on-hand figures shop owners see, and a store that has already hand-corrected the gap with an Adjustment would end up under-counted unless that adjustment is found and reversed.

Blast radius

From the code: every product, for every customer using this ledger, that has at least one Return movement has on-hand stock overstated by the total quantity of all its returns. The error builds up, so a product with several returns drifts further, and a return of N units adds an N-unit gap, not 1. Purchases, sales and adjustments are not affected. The movement report is correct, so the shop owner's report shows the true figure while the system's on-hand number is too high. That can lead to selling stock that doesn't exist. I could not count affected customers, products or return movements because this run has no database, log or APM source.
